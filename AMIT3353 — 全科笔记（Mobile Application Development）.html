💡 Monolithic vs Microkernel（slide 完全没解释）

Monolithic kernel（Linux）：驱动程式、档案系统全部塞在 kernel 里 → 快，但一个驱动当掉整个系统跟着当。

Microkernel：kernel 只留最核心的（排程、记忆体、行程间通讯），其他都推到外面当一般程式 → 稳定、安全、容易移植到不同装置，代价是模组间沟通多一层、稍慢。

这就是 Harmony 和 Fuchsia 选 microkernel 的原因：它们的目标是同一套 OS 跑在从手表到汽车的所有装置上。被追问时讲得出这点会很加分。

6. Android Application Fundamentals

6.1 APK 里有三样东西

Android package (APK) = Compiled Code + Resources + Data

  • Compiled code：Kotlin / Java 编译后的 DEX 档 + C++ 的 native library
  • Resources：图片、layout、字串、颜色、menu、动画
  • Data / 其他：AndroidManifest.xml、签章、assets
✅ Slide 42 Q1 — 为什么 APK 要包含三个不同的部分？

因为三者的角色不同：code 是行为（做什么）、resource 是外观与文字（长什么样）、data / manifest 是宣告与设定（有哪些 component、要什么权限）。

把 resource 和 code 分开的好处是同一份 code 可以配不同的 resource——换语言（英文 / 马来文）、换萤幕尺寸、换深色模式，都不用改 code，系统在执行时自动挑对应的 resource。这正是 MyGOV 能做到 multilingual 的基础。

6.2 Security Sandbox

每个 Android app 住在自己的安全沙盒里。五句话（考试照这五点写就够）：

  1. 每个 app 对 OS 来说是一个不同的使用者
  2. 系统给每个 app 一个独一无二的 Linux User ID (UID)
  3. 系统为该 app 的所有档案设定权限，只有那个 UID 能读写
  4. 每个 app 跑在自己的 Linux process 里
  5. 每个 process 有自己的 virtual machine (VM)

类比：公寓大楼。每个 app 是一间单位，UID 是门牌号码，Linux 的档案权限是门锁。你只能进自己那间；要进别人家必须对方开门（Content Provider）或管理处批准（permission）。

💡 补充：这个 VM 叫 ART

Slide 只写「its own virtual machine」。这个 VM 是 ART（Android Runtime），自 Android 5.0 起取代旧的 Dalvik VM。所有 app process 都是从一个叫 Zygote 的母 process fork 出来的，所以启动快、共用的系统类别只载入一次。考试写「its own VM」就够，能说出 ART 是加分项。

6.3 The Principle of Least Privilege

最小权限原则：每个 app 预设只拿到完成工作所需的最低限度存取权，多一分都不给。没有被授权的部分，app 完全碰不到。

沙盒是手段，最小权限是目的——这两个概念常被混着问，要分清楚。

6.4 共用资料的条件

  • 两个 app 使用相同的 Linux user ID → 就能读写对方的档案
  • 条件：两个 app 必须用同一张凭证（certificate）签署
  • 附带效果：它们跑在同一个 Linux process、共用同一个 VM，节省系统资源
⚠️ Slide 没说的：这个做法已经被弃用

sharedUserId 自 API 29 起被官方 deprecated，因为它破坏沙盒隔离，而且一旦在已发布版本设定就无法移除。现在的正规做法是 Content Provider + 自订 permission。

考试策略：题目问「两个 app 如何共用资料」→ 照 slide 答 same UID + same certificate（这是考点）。问「建议一个安全的做法」→ 答 Content Provider。

6.5 Permission

  • App 可向使用者请求权限存取装置资料：contact、SMS、storage、camera、Bluetooth、location 等
  • Android 5 及以下：所有权限在 install time 一次过批准（不给就不能装）
  • Android 6 及以上：在 runtime 请求（用到才问，用户可单独拒绝某一项，也可事后到设定关掉）

为什么要改成 runtime？因为 install-time 是「全有或全无」——用户为了装 app 只好全部接受，等于没有选择。Runtime permission 让用户在具体情境下判断（「这个 app 现在要开相机做什么？」），符合最小权限原则。

补充（不在 slide）：即使在 Android 6 以上，normal permission（如 INTERNET、振动）仍是安装时自动给的，只有 dangerous permission（相机、定位、联络人、麦克风）才需要 runtime 请求。Android 13 起连通知（POST_NOTIFICATIONS）也要 runtime 请求。

✅ Slide 42 Q2 — Android 保护 app 资料与使用者安全的两个方式
  1. Application sandbox（UID 隔离）：每个 app 被指派独立的 Linux UID，跑在独立的 process 和 VM 中，档案权限只允许该 UID 存取，因此一个 app 无法直接读取另一个 app 的资料；就算某个 app 被入侵，损害也被关在它自己的沙盒里。
  2. Permission 机制（最小权限原则）：app 预设没有任何存取装置敏感资料的权力，必须在 manifest 宣告并取得使用者同意（Android 6 起是 runtime 逐项批准）才能存取相机、定位、联络人等，使用者随时可以撤回。
💬 答题句 (EN)

Android protects user data in two main ways. First, the application sandbox: the system gives every app a unique Linux user ID and runs it in its own process with its own virtual machine, and file permissions allow only that UID to access the app's files. Second, the permission model: by default an app has access only to what it needs (the principle of least privilege), and it must declare permissions in the manifest and obtain the user's consent — granted at runtime from Android 6.0 onwards — before accessing sensitive resources such as the camera, location or contacts.

7. 四大 App Components：A-B-C-S 高频

记忆法：Slide 自己给的 ABCS — Activities、Broadcast Receiver、Content Provider、Services。

7.1 Activity

  • 一个 Activity = 一个画面（screen）
  • 提供一个 window 来画出使用者介面（UI）
  • 一个 app 通常由多个 activity 组成
  • 其中一个是 "main" activity，是启动 app 时开的那一个

MyGOV 的例子：登入画面、服务目录、申请表单、付款画面——每一个都是一个 Activity。

7.2 Broadcast Receiver

  • 是系统与 app 之间的讯息系统（messaging system）
  • 没有 UI，但可以发出 status bar notification
  • App 必须先注册（register）才能收到某个事件
  • 系统广播会送给所有订阅了该事件的 app，例如 battery low、system reboot

7.3 Content Provider

  • 管理对一个中央资料仓库的存取
  • 资料可以存在：file system、SQLite database、网络／云端
  • 提供持久性储存位置（persistent storage）
  • 其他 app 可以查询、甚至修改这些资料（需要权限）
  • 例子：User Dictionary（你打字学过的词）；Contacts、MediaStore 也是

7.4 Service

  • 没有 UI，在背景执行
  • 执行长时间的操作，或为远端 process 工作
  • 例子：背景播音乐、透过网络抓资料
  • 由另一个 component 启动（例如 Activity 启动它）
⚠️ 最常见的误解：Service ≠ 另一条 thread

Service 预设仍然跑在 main thread（UI thread） 上。如果你在 Service 里做耗时工作而不另开 thread，一样会卡住 UI（ANR）。Slide 说「long-running operations」很容易让人误会。

补充（不在 slide）：从 Android 8.0 起背景 service 有严格限制，长时间工作要用 Foreground Service（必须显示通知）或 WorkManager。

8. Component 之间怎么互相启动，与 Intent

Slide 52 提出的问题：既然 Android 把每个 app 关在独立 process、用档案权限互相隔离，那一个 app 要怎么启动另一个 app 的 component？

答案是：

  • 一个 app 可以启动另一个 app 的 component
  • Android app 没有单一进入点，没有 main() function
💡 「没有 main()」为什么重要

传统程式（C、Java 桌面程式）从 main() 开始跑到结束，程式自己控制流程。Android 相反：系统随时可以从任何一个 component 进入你的 app——用户点图标进 MainActivity、点通知进另一个 Activity、系统广播叫醒 Broadcast Receiver。

流程由系统控制，你的 code 只是回应 callback。这叫 inversion of control，也是为什么 Chapter 3 要学 lifecycle。

8.1 Intent

  • 用 Intent 来启动 Activity、Service、Broadcast Receiver（三种，Content Provider 除外）

✅ Slide 60 的答案

1. Intent class 的用途是什么？

Intent 是一个讯息物件（messaging object），用来在 component 之间传递「要做什么」的请求。它让一个 component 可以启动 Activity、启动 Service 或发出 Broadcast，并且可以跨 app（由 Android 系统居中媒合），同时还能携带资料（extras）给目标 component。

2. 三个常见用途：

启动 Activity（startActivity(intent)）— 开一个新画面；启动 Service（startService(intent)）— 叫背景工作开始；传送 Broadcast（sendBroadcast(intent)）— 通知所有订阅者某事件发生。

3. Manifest file 为什么对每个 Android app 都重要？

因为它是 Android 在启动任何 component 之前读的第一个档案，系统靠它知道这个 app 有哪些 component 存在。没有在 manifest 宣告的 component，对 Android 来说等于不存在，永远不会被执行。它还声明 permission、最低 API level、需要的硬体/软体功能与函式库，系统与 Play Store 都靠它决定这个 app 能不能装、能不能用某些功能。

💬 答题句 (EN)

An intent is a messaging object used to request an action from another component. It can start an activity, start a service, or deliver a broadcast, and it can carry data as extras. Because an app has no single entry point and no main() function, the Android system receives the intent and locates a matching component — which may belong to another app — so the two apps never contact each other directly and the sandbox is preserved.

B1. The principle of least privilege means that by default each app is granted access only to the components it requires to do its work, and no more; an app cannot access any part of the system for which it has not been given permission. The system enforces this in two layers. First, the application sandbox: each app receives a unique Linux user ID, runs in its own process with its own virtual machine, and its files are protected by permissions tied to that UID, so apps are isolated from one another by default. Second, the permission system: access to sensitive resources such as the camera, location, contacts or storage must be declared in the manifest and approved by the user — at runtime from Android 6.0 onwards — and the user can revoke it at any time.

D. Thinking (2)

  1. Android keeps every app in its own sandbox so that apps cannot see each other's data. Why, then, can WhatsApp open the gallery app to let you pick a photo? Does this contradict the sandbox? (6 marks)
  2. The slides say two apps can read and write each other's files if they share the same Linux UID. If this is so convenient, why did Google later discourage it? (6 marks)
Answers — D

D1. There is no contradiction, because the two apps never contact each other directly. WhatsApp does not read the gallery app's files; it sends an intent to the Android system saying that it needs a component that can "pick a photo". The system locates and starts the matching activity in the gallery app, the user personally selects a photo inside the gallery's own screen, and the system then returns access to only that one selected item to WhatsApp. The OS acts as the intermediary and the user acts as the authoriser. WhatsApp never receives permission to read the whole gallery folder — it receives only what the user explicitly chose, which is the principle of least privilege in practice rather than an exception to it.

D2. There are three problems. First, it breaks the sandbox isolation: sharing a UID removes the security boundary between the two apps, so if one of them is compromised the attacker immediately gains all the data of the other, defeating the purpose of the sandbox. Second, it is irreversible: once sharedUserId has been set in a published version it cannot be removed in a later update without the system treating the app as a different app and losing the user's data, so it is a permanent commitment. Third, there is a safer alternative: a content provider with custom permissions gives fine-grained, per-item control — exposing only the specific data that needs to be shared rather than the whole file space — and access can be revoked. For these reasons sharedUserId has been deprecated since API 29.

4. Navigation Principles（2.2）★

五条原则：

  1. Fixed start destination（固定起点）
  2. Navigation state 是一个 destination 的堆叠
  3. Up 和 Back 在 app 内部行为相同
  4. Up 永远不会离开 app（但 Back 可能会）
  5. Deep linking 模拟手动导航
✅ Slide 11 的问题：为什么 Back 和 Up 的行为必须不一样？

因为两者的作用范围不同。Back 是系统级按键，照使用者实际操作历史一步步退，可能退出 app、回到上一个用过的 app，甚至到桌面。Up 是 app 内按钮，只沿着开发者定义的层级结构往上走，永远不离开这个 app——即使使用者是从通知或深层连结直接跳进来（没有经过上层画面），Up 也会先补上该有的父层画面。如果两者行为相同，从通知跳进深层画面后按返回会直接把使用者丢出 app，打乱他对 app 结构的理解。

5. Fragment（2.2）

Fragment = Layout + Code，一个可重用的 UI 模组，必须寄生在一个 Activity 里，不能独立存在。

一个 Activity 里可以放多个 Fragment，常见用法：横屏时左右两栏（清单+详情）同时显示；直屏时拆成两页，点一项才跳进详情。

D. Thinking (2)

  1. LazyColumn only composes visible items, while a full recomposition only re-renders changed parts. Explain why these are two different optimisations solving two different problems. (6 marks)

Answers — D

D1. "Only compose visible items" solves an initial-load / memory problem — deciding how much should ever be built in the first place, avoiding composing a thousand off-screen items. "Only recompose changed parts" solves a re-render problem — once something is already on screen, deciding how little needs to be redrawn when its underlying data changes. Both can happen together: LazyColumn first decides which items to compose at all, and each composed item may later recompose independently when only its own data changes.

D2. The Back key's behaviour doesn't depend on app structure — it simply replays the system-tracked history of screens the user actually visited, which the system already knows without asking the app. The Up button's behaviour depends on a logical hierarchy the developer defines — which screen "should" sit above this one — and that is not always the same as how the user actually arrived (e.g. jumping in from a notification with no visited parent). 1. Activity 与 Back Stack

  • Activity = UI，"main" activity 是 app 的第一个画面
  • Activity 可以被同一个 app 内的另一个 activity启动，也可以被别的 app启动
  • 必须在 Manifest File 宣告才能被系统存取（跟 Ch1 讲的「未宣告的 component 不存在」是同一件事）
<manifest ... >
  <application ... >
    <activity android:name=".ExampleActivity" />
    <activity android:name=".SecondExampleActivity" />
  </application>
</manifest>

关闭 Activity 的两个方法：finish()——关掉当前这个 activity；finishActivity()——关掉之前用 startActivityForResult() 启动过的另一个 activity。

Back Stack（后退堆叠）

每次开新 activity，前一个就被 stop，但系统把它保留在一个堆叠里——这个堆叠是 Last In, First Out (LIFO)。使用者按 Back 键时，最上层的 activity 被 pop 出去，堆叠里的前一个恢复（resume）。

✅ Slide 12 的四个问题（没给答案）

1. Activity 在 Android 里的主要用途是什么？

Activity 提供一个视窗（window）来画出使用者介面，是使用者能实际看到、能互动的一个画面。一个 app 通常由多个 activity 组成，其中一个是 main activity。

2. 为什么 Activity 一定要在 manifest 宣告？

因为 manifest 是系统启动任何 component 前读的第一个档案，没有宣告的 activity 对系统来说等于不存在，永远不能被启动——这跟 Ch1 讲的规则完全一致。

3. Android 用什么资料结构管理 app 的 component？

Stack（堆叠），且是 Last In First Out (LIFO)。新开的 activity 推到最上面，Back 键把最上面的弹出。

4. 使用者离开一个 Activity 后，它会发生什么？

它会被stop，但保留在 back stack 里，不会立刻被销毁；只有在系统需要回收记忆体，或使用者一路按 Back 把它弹出堆叠，它才真正走到 onDestroy。

💬 答题句 (EN)

An explicit intent names the exact component to start — typically the package name or fully-qualified class name — and is used to launch another activity within the same app; the system only searches that app's own components, so it is guaranteed to find a match. An implicit intent declares a general action to be performed without naming a component, and the system searches every installed app's intent filters for a match; if none is found the app crashes unless the caller checks first, and if several apps match, the system shows the user a chooser dialog.

2.4 Intent Filter

用 <intent-filter> 向系统宣告自己的 app 能接收哪些 implicit intent：

<activity android:name="ShareActivity">
  <intent-filter>
    <action android:name="android.intent.action.SEND"/>
    <category android:name="android.intent.category.DEFAULT"/>
    <data android:mimeType="text/plain"/>
  </intent-filter>
</activity>

这段宣告的意思是：「我能处理别人送来的 ACTION_SEND、资料类型是纯文字的 intent」——例如别的 app 想分享一段文字时，这个 activity 就有机会出现在选择清单里。

⚠️ API 30+ 的额外规则

Android 11（API 30）起，如果你的 app 想用 implicit intent 去查询、启动别的 app，必须先在自己的 manifest 用 <queries> 宣告你关心哪些类型的 app（例如浏览器、相机、相册），否则系统会限制你查询到的结果，即使对方 app 确实存在。

✅ Slide 38 的问题

1. Explicit 和 implicit intent 最主要的差别是什么？

Explicit 指名确切要启动的 component，只在自己 app 内搜寻，一定成功；Implicit 只宣告要做的动作，系统在所有 app 的 intent filter 里搜寻，可能找不到（crash）或找到多个（弹出选择）。

2. 判断三个情境：

a. 分享一个网址 → Implicit（ACTION_SEND，交给任何能处理文字/网址分享的 app）　b. 播放从网络下载的音讯档 → Implicit（ACTION_VIEW + 音讯 MIME type，交给装置上的音乐播放 app）　c. 把手机音效改成静音模式 → Implicit（这类系统设定通常没有对应的「自己 app 内」画面，需要靠系统层级的 intent 或 API 处理，不属于自己 app 的 component）

六个 Callback 该做什么

Callback什么时候该做的事
onCreate建立 activity，整个生命只做一次建 UI（setContent{}）、设 ViewModel/LiveData、注册 observer、检查权限
onStart变成可见注册 BroadcastReceiver、开始动画、载入轻量 UI 资料

onPause使用者正在离开，不一定被销毁；多窗格下仍可能可见快速储存未存的资料；动作必须很短；停掉耗 CPU 的动画/媒体/即时更新

onDestroyfinish() / 系统回收 / 转屏释放全部资源；系统可能直接跳过这个 callback
💬 答题句 (EN)

onCreate performs one-time setup such as building the UI and initialising class-scope objects. onStart makes the activity visible. onResume brings it into the foreground and interactive. onPause means the user is leaving — it must execute briefly, and any unsaved data should be committed here, since the system may kill the process right after onPause without ever calling onStop or onDestroy. onStop releases resources once the activity is fully invisible, and onDestroy performs final cleanup, though the system may skip it entirely.

            override fun onResume(owner: LifecycleOwner) {
                Log.d("Lifecycle", "onResume - UI Fully Interactive")
            }
        })
    }
}
✅ Slide 59 的四个问题

1. onCreate 和 onPause 为什么对 Activity 很重要？

onCreate 是唯一保证只跑一次的初始化时机，UI 与核心物件都在这里建立；onPause 是最后一个确定还会被呼叫的时机——系统随时可能在 onPause 之后直接杀掉 process 而跳过 onStop/onDestroy，所以任何「不能丢失」的资料都要在 onPause 存好。

2. 什么情境下 onPause 和 onStop 不会被呼叫？

当系统直接终止整个 app process时（例如记忆体极度不足、或使用者从「最近使用的 app」清单把它滑掉），系统可能不会照顺序呼叫这些 callback，而是直接结束 process。

3. 各任务该放在哪个 callback？

a. 播放背景音乐 → onStart / onResume 开始播放（对应在 onPause/onStop 停止）　b. 存游戏进度 → onPause（快速存）搭配 onStop（更完整的存档）　c. 建立与伺服器的连线 → onStart（对应在 onStop 断线）

4. Activity 转换状态时，哪两个 callback 适合用来存资料库？

onPause（存下最关键、不能丢的部分，要快）和 onStop（这里可以做比较完整、稍花时间的资料库写入，因为画面已经完全不可见）。

5. Configuration Change 与 Compose

Configuration change（例如转屏、切换语言、接上外接键盘）会让目前的 activity 被销毁重建，正常走一次 onPause → onStop → onDestroy，然后重新 onCreate。这也是 Ch1 提过「记忆体不足会杀 process」那条伏笔在这里的另一半：转屏和记忆体不足都会导致 activity 走到 onDestroy，差别只在于转屏之后系统会立刻重建它，而记忆体不足未必会（要等使用者自己导航回来）。

6. 保存与还原 Instance State

Instance state = 系统用来还原前一个状态的资料，是一组 key-value pairs 存在 Bundle 物件里。系统用它来记住每个 UI component 的状态，例如使用者在文字框里还没送出的输入。

lateinit var textViewMsg: TextView

override fun onSaveInstanceState(outState: Bundle?) {
    outState?.run { putString(MSG_VIEW_KEY, textViewMsg.text.toString()) }
    super.onSaveInstanceState(outState)   // 别忘了呼叫父类别，保存 view hierarchy 本身
}

override fun onRestoreInstanceState(savedInstanceState: Bundle?) {
    textViewMsg.text = savedInstanceState?.getString(MSG_VIEW_KEY)
}
✅ Slide 63 的问题

现代装置常见多窗格/多任务，身为开发者该如何处理窗格/任务切换时不丢失重要资讯？

在 onSaveInstanceState() 里把使用者还没送出、不能重新产生的资料（例如表单填了一半的内容）存进 Bundle，并在 onRestoreInstanceState() 或 onCreate 收到的 savedInstanceState 里读回来，重新填回对应的 UI component。对于比较大或需要跨转屏存活的资料（不只是切换窗格），改用 ViewModel，因为它能在 configuration change 中存活，不需要每次都靠 Bundle 序列化/反序列化。两者搭配：Bundle 处理「系统可能整个 process 被杀」的最坏情况，ViewModel 处理「只是转屏或切分割画面」的一般情况。

B. Short answer (3)

  1. Explain why an implicit intent can fail at runtime even though the code compiles correctly, and how a developer should guard against this. (5 marks)
  2. MyGOV wants to save a partially-filled licence renewal form if the user is interrupted by a phone call. Explain the mechanism that makes this possible. (5 marks)
  3. Explain the relationship between onPause and the system's ability to skip onStop and onDestroy. (5 marks)
Answers — B

B1. An implicit intent only declares an action to be performed, not a specific component, so at runtime the system must search every installed app's intent filters for a match. Whether a match exists depends entirely on what apps happen to be installed on that particular device — something the compiler cannot check. If no app declares a matching intent filter, calling startActivity() throws an ActivityNotFoundException and the app crashes. To guard against this, the developer should call intent.resolveActivity(packageManager) before starting the activity, and only proceed (or show a fallback message) if it returns a non-null result; for apps targeting API 30 and above, the app must also declare the relevant intents in a <queries> element in the manifest, or the system may hide matching apps from the query regardless.

中文：implicit intent 的成败取决于装置上装了什么 app，跟 code 本身对不对无关，这是回答「为什么会 crash」的关键。

B2. When the user is interrupted, the activity moves through onPause and possibly onStop, and MyGOV should save the form's current field values as key-value pairs into a Bundle inside onSaveInstanceState(). If the activity is later destroyed and recreated — whether because the system needed memory or because of a configuration change — the system passes that same Bundle back into onCreate() (or into onRestoreInstanceState()), and the app reads the saved values back into the form fields. This round trip is what lets the draft survive an interruption without the user needing to retype anything, as long as the activity isn't fully destroyed by the user manually finishing it.

中文：关键词是「Bundle 往返」——存进去、可能中间发生任何事、读回来，跟中间到底发生什么无关。

B3. onPause is the last callback the system guarantees to call before it might terminate the app's process outright — for example when a higher-priority app urgently needs memory. Once onPause has run, the system is free to kill the process at any point, which means onStop and onDestroy are not guaranteed to run; they are best-effort cleanup steps that happen only if the system has time and reason to call them in an orderly shutdown. This is exactly why any data that absolutely must not be lost has to be committed inside onPause itself, executed quickly, rather than deferred to onStop or onDestroy.

中文：这题的分数在于讲清楚「保证」和「可能被跳过」的因果关系，不是只背出六个 callback 的名字。

  1. For each MyGOV task, decide explicit or implicit and justify: (a) opening the user's uploaded documents list within MyGOV itself (b) sharing a completed application receipt via WhatsApp (c) opening the phone's default calculator app from a fee-estimation screen.
  2. A user is filling in the licence renewal form when a low-battery warning notification arrives and briefly covers part of the screen. Trace which lifecycle callbacks fire and why the form data is not lost.
  3. MyGOV's onPause callback currently makes a slow network call to log analytics. Explain why this is a design mistake and how it should be fixed.
Answers — C

C1. (a) Explicit — the documents list is MyGOV's own activity, so it can be named directly. (b) Implicit — sharing must be handed off to whichever app the user has installed for messaging (WhatsApp, or a chooser if several apps can handle it); MyGOV does not own WhatsApp's component. (c) Implicit — the calculator is a separate app the device happens to have installed; MyGOV has no explicit reference to its component.

C2. A notification banner briefly covering part of the screen does not fully hide the activity, so it only triggers onPause — the activity is still partially visible (multi-window-like state) and is not stopped. Because the system guarantees onPause will run, MyGOV should have already committed the form's field values into a Bundle the moment onPause fires (or continuously, via a ViewModel), so even in the unlikely event the process were killed at this point, the data survives. Once the user dismisses the notification, onResume fires and the form simply continues as before — onStop/onDestroy are not involved at all in this particular interruption.

C3. This is a mistake because onPause must execute very briefly — the next activity's onResume cannot proceed until the current activity's onPause finishes, so a slow network call here will make the UI feel frozen or unresponsive during every transition away from this screen, and on unreliable mobile networks the delay could be several seconds. The fix is to move the network logging out of onPause and into a background-safe mechanism that does not block the lifecycle transition — for example dispatching it via a coroutine on a background dispatcher, or queuing it with WorkManager so it runs independently of whether the user is currently switching away from the activity.

D. Thinking (2)

  1. Explain why Android gives developers two separate mechanisms — the back stack and onSaveInstanceState/Bundle — instead of just one, when both seem to be about "not losing what the user was doing". (6 marks)
  2. An implicit intent can result in a chooser dialog showing multiple matching apps. Why doesn't this happen with an explicit intent, and what does that reveal about what "resolution" actually means for each type? (6 marks)
Answers — D

D1. They solve different problems at different scopes. The back stack preserves the user's navigation history between whole screens — which activities they opened and in what order — so pressing Back returns them to a previous screen exactly where they left it, without any of the activities on the stack needing to do anything special; the system manages this automatically. onSaveInstanceState/Bundle preserves the internal state within a single activity instance — the exact values a user typed into fields — across an event that destroys and recreates that specific instance, such as a rotation or a low-memory kill. The back stack answers "where was the user in the app", while the Bundle answers "what had the user typed on this one screen"; an app needs both, because surviving on the stack does nothing to protect unsaved field values if that particular activity instance gets destroyed and rebuilt.

D2. An explicit intent already names the exact component to start, so "resolution" for it is trivial — the system simply confirms that component exists in the specified app and launches it; there is nothing to choose between, because only one candidate was ever named. An implicit intent, by contrast, only describes an action and lets the system search across every installed app's intent filters, so "resolution" here genuinely means finding candidates — and if more than one app declares a matching filter, the system has no basis for picking one over another, so it defers the decision to the user via a chooser. This reveals that "resolution" means something fundamentally different for the two types: for explicit intents it is a lookup (confirming one known target), while for implicit intents it is a search (discovering possibly many, possibly zero, unknown targets).

5. ViewModel、Repository、LiveData、Coroutine 高频

5.1 ViewModel — 为什么需要它

ViewModel 提供 UI 需要的资料，而且能在 configuration change（如转屏）中存活。这跟 Ch3 讲的「转屏会销毁重建 activity」直接相关——ViewModel 就是为了解决那个问题而存在的。

💬 答题句 (EN)

A ViewModel holds UI-related data and survives configuration changes such as screen rotation. When rotation destroys and recreates the activity, the same ViewModel instance is reattached to the new activity, so the data does not need to be re-fetched — unlike storing data directly in the activity, which is lost every time the activity is destroyed and would need to be recreated, for example by re-running a network request.

5.2 Repository — 多个资料来源的中介

Repository 提供对多个资料来源的存取，管理查询用的执行绪，让你可以同时用多个 backend。例如：Repository 实作「该从网络抓资料，还是用本地资料库的快取」这个判断逻辑。

✅ Question 4.1.4

Activity、ViewModel、Repository 各自的用途？

Activity：绘制 UI、接收使用者互动。ViewModel：持有 UI 需要的资料，能在 configuration change 中存活。Repository：提供储存与载入 app 资料的 API，决定该从网络抓还是用本地快取，让 ViewModel 不需要知道资料来源的细节。

5.3 LiveData

LiveData 是一个可观察的资料持有类别，当它持有的资料改变时会通知 observer，而且是 lifecycle-aware（知道该在什么时候通知才安全）。

D. Thinking (2)

  1. ViewModel solves the "data lost on rotation" problem differently from Bundle/onSaveInstanceState (Ch3). Explain when each is the right tool. (6 marks)
  2. Why does the Repository pattern make an app easier to test and maintain, even though it adds an extra layer between ViewModel and the actual data source? (6 marks)
Answers — D

D1. Bundle/onSaveInstanceState is the right tool for small, serialisable pieces of UI state that must survive even a full process death (not just a configuration change) — such as the text currently typed into a field — because the Bundle is explicitly saved and restored by the system across that boundary. ViewModel is the right tool for larger or more structured data that only needs to survive configuration changes (not a full process kill) — such as a fetched list of results — because it avoids the overhead of serialising everything into a Bundle and simply keeps the same object alive in memory. In practice, robust apps use both: ViewModel for the bulk of the UI state, and a small Bundle save for the few fields that must also survive a process death.

D2. Without a Repository, the ViewModel would need to know the concrete details of every data source — how to query Room, how to call the network API, how to decide which one to trust — which couples the ViewModel tightly to those implementations. With a Repository, the ViewModel only depends on a simple interface ("give me the current data"), so the actual data source can be swapped, mocked, or changed (e.g. adding a cache, switching APIs) without touching the ViewModel or UI at all. This also makes testing easier: a test can substitute a fake Repository that returns known data instantly, without needing a real database or network connection.

1. 解释 mobile app、API、back-end 三者的关系

Mobile app 是前端介面，负责跟使用者互动；API 是两端沟通的规则与管道，定义前端可以请求哪些操作、传什么格式的资料；back-end 是实际处理请求、存取资料库的伺服器端逻辑。App 透过 API 向 back-end 发出请求，back-end 处理完再透过 API 把结果传回。

2. 为什么网络相关工作不该放在 UI thread？

网络操作涉及不可预期的延迟（对方伺服器慢、网络不稳定），若放在 UI thread 会直接冻结整个画面，使用者点不了任何东西；系统甚至会主动丢出 NetworkOnMainThreadException 阻止这种写法，强制开发者把网络工作移到背景执行绪。

4. 网络操作：AsyncTask ＆ Volley

权限：INTERNET + ACCESS_NETWORK_STATE。最佳实践：①尽量少传敏感资料 ②所有流量走 SSL。

使用条件：必须是 private subclass；至少覆写 doInBackground(Params…)；通常也覆写 onPostExecute(Result)；只适合短时间的操作。

Volley（HTTP library）：把资料填到 UI（main thread），例如显示搜寻结果；不适合大型下载或串流；支援 String、Image、JSON。好处：自动排程网络请求、多个并行连线、支援优先顺序、支援取消请求。三种 request：StringRequest、JsonObjectRequest、JsonArrayRequest。RequestQueue 需要 network + cache；常用网络的 app 建议用 singleton pattern 封装 RequestQueue，避免重复建立。

✅ 4.2.1 Question 3

解释 AsyncTask 在网络操作中的用途

AsyncTask 让一个耗时工作能自动在正确的执行绪间切换：onPreExecute() 在 UI thread 做准备（例如显示 loading）、doInBackground() 在背景 thread 执行真正的网络请求、onPostExecute() 再回到 UI thread 把结果显示出来，开发者不需要自己手动管理 thread 切换，只需覆写对应的方法。它适合短时间的网络操作，较长或需要精细控制的场景建议改用 coroutine 或 WorkManager。

5. MQTT

Message Queuing Telemetry Transport：跑在 TCP/IP 之上的 machine-to-machine 连线协定，使用 publish/subscribe 传输模式。

✅ 4.2.2 Question：为什么 MQTT 适合用来跟 IoT 装置沟通？

MQTT 是轻量协定，封包开销小，适合频宽有限、连线不稳定的 IoT 环境；publish/subscribe 模式让一个装置的状态变化可以同时广播给多个订阅者，不需要为每个接收方各建一条连线；同时它是即时（real-time）的，很适合 IoT 场景常见的「状态一变就要立刻通知」需求（例如感测器侦测到异常要马上推播）。

✅ 4.2.3 Questions

1. 比较订阅式（BaaS）与传统 DIY 伺服器方案

DIY 给开发团队完全的掌控权，能针对特殊需求深度客制，但要自己承担安全、效能、可靠度、维运人力的全部责任，前期开发时间也较长。订阅式（BaaS）省下大部分基础建设与维运工作，能更快上线、随用量弹性扩展，但持续产生费用（用越多付越多），而且部分核心逻辑与资料掌控权交给了第三方平台，需要评估其安全性与合规性是否符合需求。

2. H&H 案例：搜寻慢、地区管理效率差，要加 push notification 与 chatbot，怎么用最安全且最省成本的方式部署？

建议采用 BaaS（如 Firebase）而非自建伺服器：Push notification 直接用 Firebase Cloud Messaging，不需要自己维护推播基础建设；chatbot 可以用 BaaS 平台提供的 custom code integration（如 Cloud Functions）串接现成的对话服务，而不是从零开发自然语言处理系统。这样能用最低的前期投入快速上线两项新功能，同时利用平台既有的使用者身份验证与资料加密机制处理安全性，比自建伺服器更快、更省成本，也更不容易因为自行维运不当而出现安全漏洞。

B. Short answer (3)

  1. Define front end and back end, and illustrate the mobile system architecture connecting them with a diagram. (9 marks)
  2. Explain why AsyncTask splits work across onPreExecute, doInBackground and onPostExecute instead of running everything in one method. (5 marks)
  3. Compare REST and SOAP in terms of supported data formats and underlying transport. (5 marks)
Answers — B

B1. The front end is the part the user interacts with directly — the mobile app's user interface. The back end runs on the server and provides the database, the API and the application's core logic. Architecture: the mobile client (front end), which may keep a local database for offline use, communicates over the network with an API server (back end), which in turn reads from and writes to a database server backed by a cloud database.

B2. The three methods run on different threads for different purposes: onPreExecute and onPostExecute run on the UI thread because they touch the UI directly (showing a loading indicator, then displaying the result), while doInBackground runs on a background thread because it performs the actual time-consuming work (a network call, for instance) that would freeze the UI if run on the main thread. Splitting them lets AsyncTask automatically move execution to the correct thread at each stage without the developer manually managing thread switches.

B3. REST supports HTML, XML and JSON and inherits standard HTTP operations (GET, POST, PUT, DELETE) directly. SOAP supports only XML, structured as an envelope with a header and body, and can run over several application-layer protocols including HTTP, SMTP, TCP or UDP, not just HTTP.

D. Thinking (2)

  1. WorkManager and Foreground Service both run background work, but the decision tree places them at opposite ends ("depends on conditions" vs "now or never"). Explain what fundamentally distinguishes when each is the right choice. (6 marks)
  2. Why might a government app like MyGOV be more cautious about using a third-party BaaS than a typical consumer app, even though BaaS is generally faster and cheaper? (6 marks)
Answers — D

D1. The distinguishing factor is urgency and user expectation, not just "is it background work". WorkManager is for work the user does not need to see happen immediately and that the system can freely delay or batch to save resources — the trade-off it accepts is flexible timing in exchange for efficiency. A Foreground Service is for work the user explicitly initiated and is actively waiting on, where delaying it would break their expectation (e.g. an upload they just tapped "submit" for) — it accepts the cost of a persistent notification and continuous execution in exchange for guaranteeing the work happens right away and runs to completion.

D2. A government app handles sensitive citizen data — identity information, payment details, application records — under legal and public-trust obligations that a typical consumer app does not carry. Using a third-party BaaS means that data, or at least parts of the processing pipeline, passes through infrastructure the government does not fully control, raising questions about data residency (where the data is physically stored), compliance with national data-protection regulations, and the platform provider's own security practices. The speed and cost savings BaaS offers have to be weighed against these accountability requirements, which is why a government app might choose a more controlled DIY or hybrid approach for its most sensitive functions even at higher cost.

2. 为什么要在 onStart() 或 onResume() 才开始请求位置？

6. Geocoding 考卷 Q4a

Geocoding = 把地理位置（坐标）转换成地址（反过来是 reverse geocoding）。

好处与应用：

  1. 补偿模糊/错误的地址——拼错或不精确的地址仍能对应到正确位置
  2. 地址会变，坐标不会——街道改名或门牌重编后，坐标仍然有效

✅ 5.3 ＆ Review Questions

5.3-1. 哪些因素会影响 LBS 的精确度？

定位来源的选择（GPS vs Wi-Fi/cell，精度天差地远）、环境（室内/高楼/隧道会削弱 GPS 讯号）、priority 设定（选了省电模式精度自然下降）、装置硬体品质与卫星/基地台的可见数量。

5.3-2. 评论：「为 location-based app 建立最佳效能模型很重要」

同意，但「最佳」要按用途量身打造，不是单一标准。不同 app 的「最佳」定义不同——导航 app 的最佳模型是高精度、低延迟；天气 app 的最佳模型反而是省电优先。建立模型的价值在于提前在 accuracy／frequency／latency 三个维度上做出符合该 app 使用情境的权衡，而不是无脑全部拉到最高精度。

Review-4. 评论：「确保精确度最好的方法是用真实装置测试」

大致同意，但要补充。Mock location／模拟器测试能快速覆盖多种情境（不同坐标、不同精度）且不受实际环境限制，适合开发初期快速迭代；但模拟器无法真实反映硬体差异、室内讯号遮蔽、多路径反射等真实世界的干扰，所以正式发布前仍必须在不同品牌、不同环境的真实装置上验证，两者应该搭配使用，不是二选一。

Review-5. 位置感知如何提升使用者体验？（6 marks，需举例）

位置感知让 app 能根据使用者当下所在环境提供情境化的内容，而不是千篇一律的资讯——省去使用者手动输入位置的麻烦，也能提供只有「知道你在哪」才做得到的服务。例子：MyGOV 侦测到使用者目前在某个州属，自动把「附近的 UTC 据点」「该州属专属的政府活动」排在服务清单最前面，使用者不需要自己搜寻或切换地区设定，就能立刻看到跟自己最相关的内容，大幅缩短找到所需服务的时间。

Review-6. MyChild.com（GPS 儿童追踪）：描述 GPS 的三个限制（6 marks），并建议一个克服限制的技术（4 marks）

三个限制：①室内/建筑物内收讯不良——GPS 依赖卫星讯号，孩童在室内（学校、商场）时精度大幅下降甚至完全收不到。②耗电量高——持续开启 GPS 定位会让追踪装置的电池很快耗尽，对需要长时间配戴的儿童追踪装置尤其不利。③首次定位慢（冷启动）——GPS 需要时间锁定足够的卫星才能算出位置，紧急情况下（例如孩童走失）这个延迟可能造成家长焦虑甚至延误。
克服技术：采用Fused Location Provider，结合 GPS、Wi-Fi 与基地台三种来源——户外用 GPS 保持高精度，室内自动切换成 Wi-Fi/cell 定位以维持可用性，同时可依情境动态调整 priority（例如平时用 Balanced Power 省电，孩童离开安全区域时才切到 High Accuracy），在精度、电量与室内可用性之间取得平衡。

B. Short answer (3)

  1. Explain the difference between foreground and background location, and why background location requires a persistent notification. (6 marks)
  2. Describe three limitations of GPS and suggest one technique to overcome them. (10 marks)
  3. Relate the applications of geocoding to their relevance and benefits for a government service app. (6 marks)
Answers — B

B1. Foreground location is used while the screen is visible to the user, typically for a single request or a predefined period, such as turn-by-turn navigation. Background location continues even when the app is not visible, such as continuous family location sharing. Android requires a persistent notification for background location because the user is not actively looking at the app, so the notification is the only way to keep them aware that their location is still being tracked, preserving transparency and user trust.

B2. Three limitations: (1) poor indoor reception — GPS relies on satellite signals, which are heavily attenuated indoors. (2) high power consumption — continuous GPS use drains the battery quickly. (3) slow initial fix (cold start) — GPS needs time to lock onto enough satellites before it can compute a position, causing delay when it matters most. A technique to overcome these: use a Fused Location Provider combining GPS, Wi-Fi and cell tower data, so the app automatically falls back to Wi-Fi/cell indoors and can adjust its accuracy priority based on context to balance power and precision.

B3. Geocoding converts coordinates into addresses (and reverse geocoding does the opposite). For a government service app, it can auto-correct or validate addresses entered on application forms, help users locate the nearest physical service centre by converting their current coordinates into a readable address or vice versa, and keep historical records accurate over time even if street names or addresses later change, since the underlying coordinates remain stable.

Answers — C

C1. (a) High Accuracy — precise tracking needed continuously during activity. (b) Low Power — city-level accuracy is sufficient for weather. (c) Balanced Power — block-level accuracy is enough to detect proximity to a store.

D. Thinking (2)

  1. Explain why "passive location updates" can be a genuinely useful battery-saving technique rather than just a workaround, using a concrete scenario. (6 marks)
  2. A model of "best performance" for a navigation app and for a weather app would look completely different. Explain why building a single universal location model for every app would be the wrong approach. (6 marks)
Answers — D

D1. Passive location updates let an app receive location data that another foreground app has already computed, instead of activating its own GPS/Wi-Fi lookup. This is genuinely useful, not just a workaround, whenever an app's own need for location is secondary or low-priority — for example, a background analytics feature that just wants a rough sense of the user's city doesn't need to trigger its own location fix; if a navigation app happens to be actively running and already computing high-accuracy location, the passive listener gets that data essentially for free, avoiding a second, redundant battery cost for the same physical location.

D2. Accuracy, frequency and latency each have a real cost in battery and each app's usage pattern justifies a different point on that trade-off. A navigation app is used actively, continuously, and its core value depends on precise, low-latency positioning — under-provisioning accuracy directly breaks the feature. A weather app is used passively and infrequently, and its value doesn't change whether the location is accurate to 10 metres or 10 kilometres — over-provisioning accuracy here only wastes battery for no benefit. A single universal model would either waste battery for apps like weather, or under-serve apps like navigation; the "right" model is a function of how the location data is actually used, not a fixed technical ideal.

(i) 描述两种处理相机请求的方式（6 marks，各约 3 分）

  1. 用现有的 camera app（透过 Intent）——建立一个带 ACTION_IMAGE_CAPTURE 或 ACTION_VIDEO_CAPTURE 的 Intent，呼叫 startActivity() 把拍照工作交给装置上已经安装好的相机 app 处理，再透过 callback 拿回拍好的照片或影片。实作简单、不需要请求 CAMERA 权限，因为实际拍照的是别的 app。

(ii) 判断 MyGOV 该用哪一种，附理由（3 marks）

MyGOV 最适合用现有的 camera app（Intent 方式）。理由：MyGOV 拍照的用途通常是拍摄证件或文件照片上传（例如驾照更新的证明文件），不需要任何特殊的即时影像处理或自订预览；用 Intent 方式不必请求 CAMERA 权限，能降低使用者对隐私的疑虑、提升对政府 app 的信任感，同时开发成本更低，还能直接沿用各厂牌手机自家已经优化过的相机体验。

💬 答题句 (EN)

A mobile app can handle a camera request either by delegating to the device's existing camera app through an intent — using ACTION_IMAGE_CAPTURE or ACTION_VIDEO_CAPTURE, which requires no CAMERA permission since the other app performs the actual capture — or by building its own camera functionality with CameraX or Camera2, which gives full control over the preview and capture experience but requires requesting the CAMERA permission and considerably more implementation effort. For MyGOV, the intent-based approach is most suitable, since photographing supporting documents needs no custom capture logic, and avoiding the CAMERA permission reduces the privacy footprint expected of a government app.

Class用途

MediaPlayer 能播放本地与外部（串流）档案，支援 Android 平台内建的 codec，以及装置特有的 codec——建议使用 core media format：Audio（.3gp .mp3 .mp4 .mid .wav .ogg）、Picture（.jpg .gif .png .bmp）、Video（.3gp .mp4）。

Button(onClick = {

D. Thinking (2)

  1. The camera decision tree and the app-type decision tree from Chapter 1 (Native/Hybrid/Web) share a similar shape: they both ultimately ask "how much customisation do you actually need?" Explain why this question recurs across such different decisions in mobile development. (6 marks)
  2. Explain why Android maintains separate audio streams (music, alarms, notifications, ringer, etc.) instead of a single global volume. (6 marks)
Answers — D

D1. Both decisions trade the same two things against each other: development cost and control versus speed and simplicity. Delegating to an existing solution — a native OS's camera app, or a web/hybrid shell — is always cheaper and faster because someone else has already built and optimised it, but it only fits when the app's needs match what that existing solution already offers. The moment an app needs something the existing solution can't provide — custom camera processing, or native-only performance and device access — the only way to get it is to build it yourself, at higher cost. The question recurs because it's really asking "does my requirement exceed what the platform gives me for free", which is the central trade-off in almost every build-vs-use-existing decision in mobile development.

D2. Separate audio streams let the system (and the user) control the volume of different kinds of sound independently, because they serve different purposes with different urgency. A user might want their alarm to always be loud enough to wake them even if they've turned music down, or want notification sounds muted during a call without silencing the in-call audio itself. A single global volume would force all of these to move together, making it impossible to, for example, keep the ringer audible while listening to music at a low volume — separating the streams gives the user (and apps) fine-grained control that matches how these sounds are actually used in practice.

✅ Review Questions 1–3

1. Instant App 的好处？

让使用者不用安装就能体验 app 的核心功能，大幅降低尝试的门槛（点一个连结就能玩，不用等下载安装）；对开发者来说，能提高转换率——愿意试用的人变多了，其中一部分会因为体验好而转成正式安装。

2. Dynamic Delivery 最主要的好处？

D. Thinking (2)

  1. Explain why "same signing key" matters for both app updates (this chapter) and shared Linux UID access between two apps (Chapter 1) — what do these two requirements have in common conceptually? (6 marks)
  2. A free, ad-supported model and a free, Service-extension model both result in a $0 price tag to the user, but they are fundamentally different business models. Explain the difference and why it matters when choosing one for a sensitive-data app. (6 marks)
Answers — D

D1. Both cases use the signing certificate as proof of identity/ownership. For updates, Android will only treat a new APK as a legitimate update to an existing app if it is signed with the same certificate as the installed version — this prevents someone else from pushing a malicious "update" to your users. For sharing a Linux UID between two apps, the system requires both apps to be signed with the same certificate as proof that they come from the same trusted developer, since sharing a UID removes the sandbox boundary between them and that trust can't be granted lightly. In both cases, the certificate functions as the system's way of answering "can I trust that this came from the same place as before" — updates trust continuity, shared UID trusts common ownership.

D2. In an ad-supported model, the app's actual customer is the advertiser, not the user — the app's business depends on showing ads and often on collecting user data to target them, even though the user pays nothing directly. In a Service-extension model, there is no advertiser in the loop at all; the app's cost is absorbed because it reduces cost or adds value elsewhere (e.g. fewer support calls, better customer retention for the underlying service), and the user is genuinely just a user, not a product being monetised through data or attention. For an app handling sensitive data — financial details, identity documents, government records — this distinction matters enormously: an ad-supported model creates a structural incentive to collect and monetise user data that a Service model simply does not have, which is precisely why a government app should avoid it even though both models are "free" to the end user.
